The One Shot copy failure is reproducible and comes from several connected implementation defects. The reported instructions are application-generated fallback text. The saved board also contains broken sentences caused by word-count truncation. Improving the prompt alone will not fix either problem.

This document records the diagnosis and proposed implementation. No application code, board content, or production configuration was changed during the investigation.

Implementation update: see [the implementation and verification record](board-copy-implementation-2026-09-16.md) for subsequent code changes, test results, the reviewable repair proposal, and remaining rollout work.

1. The generation schema and validator disagree. [The schema](/Users/edmondmbadu/repo/living-wiki/functions/src/gemini.ts:817) accepts any string for `role`, while [the validator](/Users/edmondmbadu/repo/living-wiki/functions/src/board-wizard-listing-marketing.ts:569) accepts a fixed set. Replaying the cached roles through the current validator rejects seven of ten scenes: `visual_hook`, `outdoor_space` twice, `living_room` twice, `dining_area`, and `call_to_action`. Normalization changes underscores to hyphens, but does not map these names to `hook`, `outdoor`, `living`, `dining`, and `action`. Valid-looking prose is silently discarded.

2. The kitchen scene passes the role check but fails the unqualified-furnishings check because it describes “stainless steel appliances” without qualification. That rejection applies when the sale is not verified as furnished. Keeping unsupported inclusion claims out is appropriate; replacing the whole scene with an instruction is not. The saved pattern is consistent with the bedroom and bathroom scenes surviving while the other eight are replaced or left uncovered. Rejection reasons should be recorded rather than inferred after the fact.

3. Narration is planned per selected photograph, but final cards are built per room group. [The composer](/Users/edmondmbadu/repo/living-wiki/functions/src/board-wizard-listing-marketing.ts:594) groups all analyses and preserves every group, regardless of the number of planned scenes. Its fallback scene selection can spend several slots on one room. A different room can therefore have photographs but no matching scene. [The exact reported phrase](/Users/edmondmbadu/repo/living-wiki/functions/src/board-wizard-listing-marketing.ts:658) is hardcoded for that case. Increasing the scene count only reduces the probability; it does not establish coverage.

4. [The short-narration fallback](/Users/edmondmbadu/repo/living-wiki/functions/src/board-wizard-listing-marketing.ts:1073) takes the first `round(seconds × 2.6)` words and appends a period. At five seconds it keeps 13 words. A local replay reproduced the exact “Shown staged with.” sentence. The generated scenes themselves contain 16–20 words despite claiming five seconds, so the duration field is also not a measured duration.

5. Composition changes the story after it has been written. The overview borrows a room scene, explaining the identical overview/living narration. `completeStoryScenes` appends a closing message to the last selected photo before groups are assembled; this can place closing language inside a room card or repeat it in a separate closing card. The final order needs to be established before writing transitions and endings.

6. No universal final copy check catches these defects. [The callable](/Users/edmondmbadu/repo/living-wiki/functions/src/index.ts:8315) shapes and enriches the generated batch, then returns it without a final public-copy acceptance gate. A listing group's `reviewStatus: verified` describes its photo classification, not the quality of its narration. [Live View](/Users/edmondmbadu/repo/living-wiki/src/app/boards/boards.ts:16712) and [video narration](/Users/edmondmbadu/repo/living-wiki/functions/src/stack-video-narration.ts:45) consume `notes`, so defects propagate into speech rather than remaining an editor-only problem.

**Why this also matters for general boards**

The generic normalizer substitutes “Review and edit this generated card before sharing the board” when `notes` is missing, and “Generated by the LivingWiki Wizard” when a non-food subtitle is missing. See [normalization](/Users/edmondmbadu/repo/living-wiki/functions/src/gemini.ts:2413). This gives a structurally valid card public-facing process text.

[Fallback style handling](/Users/edmondmbadu/repo/living-wiki/functions/src/board-wizard-narration.ts:57) adds stock openings to existing content. It does not transform sparse extraction data into useful prose. Some deterministic listing, accommodation, and restaurant branches return field lists, generic gallery labels, or “Use this card…” instructions. The general verification pass primarily checks facts, membership, and order; it is conditional and can return its draft when verification fails. It does not cover the specialized listing composer.

Source handling also limits writing quality. Listing descriptions are capped at 1,200 characters, article section excerpts at 900, and the generic article-writing prompt transmits only 500 characters per item. These limits can discard the specific facts that make copy useful. The plan should retain complete extracted material internally and select relevant evidence per card within a measured context budget.

The architecture should become: extract evidence → decide final cards → write finished copy → validate and repair → save → render consistently.

**The proposed implementation, in order**

1. **Close the confirmed failure paths first.** Introduce one shared, typed role vocabulary used by the JSON schema, prompt, parser, cache reader, and validator. Add explicit aliases for the observed legacy values; reject unknown meanings with a recorded reason. Bump the story-cache version. Replace every author-directed public fallback with a complete, evidence-based sentence. Generate a fallback for each uncovered final group, not merely each selected photograph. For uncertain photos, retain a neutral gallery label and put the review message in author-facing metadata. Replace word slicing with short sentence templates or sentence-preserving shortening; never turn an unfinished clause into a sentence by appending a period. Give the overview and closing card their own copy. Extend the existing listing regression test with this incident before changing the implementation.

   Completion criterion: replaying the reported role payload and the low-count fixture produces no instruction leakage, no dangling clauses, no reused room script as the overview, and valid copy on every audience-facing card. Keep the existing photo-gallery preservation and intentional author-only placeholder behavior.

2. **Make final cards the unit of generation.** Add a pure card planner, proposed as `functions/src/board-wizard-copy-plan.ts`. Each planned card has a stable `cardKey`, role, order, supporting fact IDs, supporting photo IDs, selected presentation photos, and length target. For listings, plan overview, represented room groups, optional authored intro, and one closing action before the writer runs. Match the response by `cardKey`; check missing, duplicate, and unexpected keys. Generate one batch of copy for the complete plan, with neighboring card context. Do not let the writer select unrelated cards or change the membership.

   Preserve full room coverage in automatic listing mode. If a user explicitly requests a fixed number of cards, combine compatible groups where appropriate and expose the resolved count; do not silently use a scene budget as a final-card budget. Calculate narration budgets from the actual audience-facing cards. Preserve all original gallery images even when fewer images participate in Live View. A grouped bedroom card must not turn several bedrooms' different features into claims about one bedroom. The claim-to-photo mapping must also ensure the described feature appears in the selected presentation photos, not only somewhere in the larger gallery.

3. **Write real estate copy from evidence and an explicit editorial brief.** Normalize facts with their source, extraction time, value, unit, applicability, and confidence. Separate visible observations from listing statements and supplied agent information. Resolve conflicting property type, address/unit, price, and bath notation before writing; never infer the correct value from the most attractive phrasing. The reported board says “Single-family home,” while the cached AI close says “condo”; that disagreement needs source verification, not a stylistic rewrite. Distinguish photographed appliances from items confirmed to convey. Treat fixed appliances, movable furnishings, and unknown inclusions as separate evidence categories instead of one blanket noun blacklist.

   Default to warm, precise prose for prospective buyers. Lead with a distinctive supported feature, then its practical significance only where evidence supports the connection. Use titles that identify the space and summaries that convey a useful takeaway. Keep photo counts in gallery UI. Five-second mode should produce one concise complete sentence; 15–30 seconds can develop two or more connected sentences when the source supports them. Do not pad sparse evidence to meet a duration. Avoid repeated tour introductions, excessive staging explanations, unsupported material identification, neighborhood/school/safety claims, demographic targeting, invented urgency, and investment promises. A source URL alone is not proof of a claim. Preserve supplied agent introductions and approved scripts verbatim unless the author chooses to rewrite them.

4. **Add a common copy acceptance and repair layer.** Add `functions/src/board-wizard-copy-quality.ts` and run it after final source shaping and composition, before the callable returns. Apply it to listing, rental, describe, URL, pasted-text, photo, menu, and commerce output with mode-specific rules. Inspect title, subtitle, notes, summary, and any alternate speech fields. Check exact card coverage, known placeholder signatures, dangling fragments, duplicated narration, inconsistent perspective, unsupported numeric claims including written numbers and units, and unsupported fact/photo references. Detect production directions contextually: “Call the agent” is a legitimate viewer action, and a tutorial may legitimately contain imperative sentences. Do not globally ban words such as “continue,” “write,” or “review.”

   Use deterministic checks for clear failures and a batched editorial check for semantic issues. Repair only failing cards, supplying their evidence and issue codes; revalidate after repair. Start with one bounded repair pass per batch. If it fails, use a validated factual fallback when evidence is sufficient. Otherwise preserve an editable draft and explicitly identify the affected cards to the author; do not silently label the result ready. Missing room evidence should not be replaced with invented details or a nonsensical sentence. Add generation-quality states separate from photo-classification confidence.

5. **Keep public copy, source material, and editor instructions distinct.** For ordinary generated cards, retain `notes` as the canonical finished narrative to minimize migration risk. Preserve title, subtitle, and `shortSummary` as distinct display roles. Store diagnostics, repair reasons, and author instructions outside public prose, with an author-facing projection. Keep source text and evidence separately where needed. For authoritative pasted scripts and quotations, preserve the source and approved wording; make any shorter spoken adaptation an explicit variant rather than overwriting the supplied text. Reuse the sentence segmentation ideas in `stack-script-shortening.ts`, but validate fragments and factual meaning as well as sentence boundaries.

   Add a small narration resolver contract used consistently by Live View, speech/video generation, translations, and document export. Keep existing tour `guideScript` and contact-card behavior explicit. Apply the existing `cardsForPublishedExperience` exclusion to every exported experience and verify it. A saved text revision must change the relevant speech, translation, trailer, and video fingerprints so previous audio/video does not keep speaking old copy. Persist supported quality/source fields through draft serialization and team save/publish paths; update allowlists where necessary.

6. **Repair existing boards through a reviewable migration.** First implement a read-only scanner for exact fallback signatures, broken fallback sentences, and missing quality metadata in `boards` and `team_boards`. Produce a per-card before/after proposal. Repair the reported team draft first using the original source, photos, cached observations where valid, and supplied introduction/contact configuration. Preserve card IDs, image order, ownership, team binding, visibility, and user-authored text. Apply through the normal team save/revision mechanism with a revision precondition, an idempotency key, and a recoverable prior revision. Skip boards changed since the scan. Do not convert a team draft into a published board. Existing rendered media must be marked stale or regenerated after approved text changes. Broader migration should use a reviewed candidate list; a code deployment by itself cannot correct already saved text.

These are illustrative replacements based on the board's stored feature labels, not newly verified listing facts or approved edits. Verify the supporting photographs before saving them. Each short example is suitable for a concise card and avoids unsupported claims about inclusions or room connections.

| Card | Proposed short copy |
| --- | --- |
| Living Areas | “Hardwood floors and a vaulted ceiling define the main living area.” |
| Kitchen | “White cabinetry and hardwood flooring give the kitchen a simple, cohesive palette.” |
| Exterior & Arrival | “Multiple balconies and white railings give the exterior a distinctive profile.” |
| Contact | “Contact Chip Watson to ask a question or arrange a private showing.” |

A longer version should add another supported detail rather than a stock sentence about continuing the tour. In general content, the same principle applies: name what is specific about the subject, explain the relevant idea, and finish the thought. For example, if a museum source establishes a shipbuilding exhibit and an interactive navigation display, use “The shipbuilding exhibit traces how vessels were constructed, while an interactive display introduces navigation.” Do not turn those facts into “Continue exploring this fascinating museum” or invent its opening hours.

**Verification and release criteria**

The functions TypeScript build and the existing listing, narration, and board-wizard quality scripts all passed during this investigation. The listing fixture nevertheless reproduced bad text. At a requested count of 4, the fixture generated 11 cards: four had the reported tour instruction and one had an internal photo-review instruction. It also duplicated overview/exterior and room/closing narration. This proves the current test suite checks important structure without enforcing finished-copy quality.

Add these focused regression and integration checks:

| Test area | Required cases and acceptance |
| --- | --- |
| This incident | Cached role names, kitchen furnishings failure, 42-photo/10-scene grouped composition, and the exact five-second truncation. Zero public process instructions or fragments. |
| Coverage | More groups than requested scenes; several images of one room; missing/duplicate response keys; rejected or empty scenes; single-card boards; unknown photos; galleries exceeding the 48-image analysis cap. Every final public card has validated copy or is explicitly withheld from ready output. |
| Claims | Furnished/unfurnished sales, rentals, built-in versus movable items, conflicting property types, decimal bath notation, source-formatted prices, written-out numbers, and features visible only in nonpresented photos. No unsupported claims in the regression corpus. |
| Writing | Five-, fifteen-, thirty-, and long-duration targets; repeated intros; room-to-room sequencing; one closing CTA; missing notes; instruction-like source content; legitimate tutorial instructions; multilingual and Unicode sentence boundaries. |
| Source fidelity | Pasted scripts, ordered lists, article excerpts, quotations, and user-authored intros survive exactly where preservation is required. Failures flag author attention rather than silently rewriting source. |
| Surfaces | Normal board and team draft → saved board → Live View → speech/video → translation/document export. Same approved content revision, no author-only reminders, no stale derived media. |
| Recovery | Model failure, malformed JSON, repair timeout, old story cache, stale board revision, and idempotent migration retry. Deterministic readable fallback or clear author-facing draft state. |

Create a versioned evaluation set of at least 30 representative inputs, including this anonymized incident, sparse listings, different property types, rentals, articles, pasted scripts, and photo boards. Repeat stochastic runs rather than trusting one attractive output. Measure instruction leakage, fragments, unsupported claims, duplicate narration, card coverage, repair/fallback frequency, p50/p95 latency, and generation cost. Hard release gates are zero known instructions/fragments/unsupported claims and complete planned-card coverage on this suite. Human reviewers should compare old and new copy blindly for factuality, specificity, coherence, natural speech, and suitability for the audience. Proposed editorial target: average at least 4/5 with no factuality failures; establish the baseline before rollout.

Record generation ID, content mode, card keys, model, prompt/schema/validator versions, source fingerprint, rejection reason counts, repair outcome, cache status, measured word counts, and final copy status. Keep production telemetry to identifiers and metrics where possible rather than raw listing/user text. Fix the deterministic defects before evaluating a model change. Use one group-writing call and a bounded batched repair to keep latency and cost predictable. Derive token budgets from actual planned cards and requested words, including long-narration cases.

Release the shared role contract and emergency copy fixes first behind a versioned switch, then the group-first writer and common validator, then the controlled existing-board repair. Start with internal/team drafts and a small canary cohort. Compare quality and latency against the baseline before expansion. Roll back by configuration if error rates, fallback rates, or latency regress; preserve created drafts and their prior content revisions.

Recommended implementation sequence: one change for regression fixtures plus the confirmed deterministic fixes; a second for the card planner and real-estate writer; a third for shared validation and rendering/persistence coverage; a fourth for the scanner and controlled migration. This ordering delivers an immediate reduction in bad copy while making the broader quality improvement measurable.
